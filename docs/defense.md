# Как объяснить и показать работу

## Что сказать в начале

«Я разработала упрощённую СУБД на Java для учёта бронирований теннисного центра. В ней три таблицы: участники, корты и бронирования. В бронировании хранятся внешние ключи участника и корта. Программа проверяет, что связанные записи существуют, а первичные ключи не повторяются.

Пользователь вводит SQL-команду. Лексер разбивает её на токены, парсер проверяет синтаксис и создаёт объект команды. Затем движок выполняет операцию. Строки и столбцы описываются отдельными классами. Хранение вынесено за интерфейс Repository.

После успешного изменения программа сериализует всю базу вместе с индексами. Сначала создаётся временный снимок, затем сохраняется предыдущая версия и заменяется основной файл. При запуске снимок загружается обратно. Если основной файл повреждён, программа пробует резервную копию.

Для быстрого поиска я реализовала AVL-индекс. Это сбалансированное бинарное дерево: в узле лежит значение столбца и первичные ключи подходящих записей. Если условие SELECT подходит для индекса, движок получает кандидатов через дерево и проверяет остальные условия. На 100 тысячах записей в моём измерении индекс рассмотрел 100 строк вместо 100 тысяч. Само время зависит от компьютера и нагрузки».

## Демонстрация по шагам

Запускать из терминала в папке проекта. Для новой демонстрации указать **новое** имя каталога, например:

```powershell
.\run.bat --data defense-session-1
```

1. Ввести `.tables`, затем `.schema bookings`. Показать три таблицы и два REFERENCES.
2. Ввести `SELECT * FROM bookings;`. Показать табличный вывод, дату, числа и BOOLEAN.
3. Добавить участника: `INSERT INTO members (id, full_name) VALUES (10, 'Тестовый участник');`.
4. Добавить несколько: `INSERT INTO members (id, full_name) VALUES (11, 'Первый'), (12, 'Второй');`.
5. Повторить вставку с id=10. Показать сообщение о повторном PK и затем `SELECT * FROM members;`.
6. Ввести `INSERT INTO bookings (id, member_id, court_id, booking_date) VALUES (10, 999, 1, '2026-11-25');`. Показать ошибку внешнего ключа.
7. Добавить правильную запись: `INSERT INTO bookings VALUES (10, 10, 1, '2026-11-25', 600, 60, 1500.0, FALSE);`.
8. Ввести `SELECT id, total_price FROM bookings WHERE total_price > 1400;`. Объяснить выбор столбцов и WHERE.
9. Ввести `UPDATE bookings SET total_price = 1800.0, paid = TRUE WHERE id = 10;`, затем `SELECT * FROM bookings WHERE id = 10;`.
10. Для сравнения планов выполнить `EXPLAIN SELECT * FROM bookings WHERE total_price = 1800;`. Сейчас будет FULL SCAN.
11. Создать индекс: `CREATE INDEX idx_price ON bookings(total_price);`. Повторить EXPLAIN: план станет INDEX idx_price (AVL).
12. Ввести `.exit`, снова запустить **тот же каталог**. Повторить запрос из пункта 11 — и запись, и индекс восстановлены с диска.
13. Ввести `DELETE FROM bookings WHERE id = 10;`. Проверить SELECT. Затем можно удалить участника 10; до удаления брони это было бы запрещено.
14. Показать произвольную схему: `CREATE TABLE notes (id INT PRIMARY KEY, text STRING);`, `INSERT INTO notes VALUES (1, 'Проверка');`, `SELECT * FROM notes;`, `DROP TABLE notes;`.
15. Выйти и выполнить `.\test.bat`, затем показать `reports/tests.txt`. Для производительности открыть `reports/benchmark.csv`; повторный замер — `.\benchmark.bat`.

## Короткие ответы на вероятные вопросы

**Это полноценная SQL-СУБД?** Это учебная реализация указанного подмножества. JOIN, OR, сортировки и пользовательские транзакции не поддерживаются.

**Чем индекс отличается от самих данных?** Данные — строки таблицы. Индекс — дополнительная структура, которая по значению столбца даёт PK нужных строк.

**Зачем балансировка?** Без неё последовательная вставка ключей могла бы превратить бинарное дерево в цепочку. AVL поддерживает логарифмическую высоту.

**Какая сложность?** Полный просмотр — O(N). Поиск через AVL — O(log D + K), где D — число различных непустых значений, K — размер результата. Для чтения всех K результатов всё равно требуется O(K).

**Почему не хранится индекс отдельно?** Схема, записи и узлы индексов сериализуются в один снимок. Они восстанавливаются в согласованной версии; отдельный файл заданием не требуется.

**Что при ошибке в середине INSERT нескольких записей?** Изменения готовятся отдельно. Если хотя бы одна строка ошибочна, ни одна строка этой команды не публикуется и снимок не сохраняется.

**Что при закрытии через диспетчер задач?** Подтверждённые изменения уже сохранены. При запуске читается основной снимок; если он повреждён, пробуется предыдущий. В последнем случае возможно потерять последнюю команду. При отключении питания абсолютной гарантии нет.

**Что при двух процессах?** Первый удерживает блокировку файла. Второй получает ошибку открытия. После завершения первого ОС освобождает блокировку, даже если процесс завершён аварийно.

**Почему операция записи медленнее?** Ради простой согласованности изменяемая таблица копируется, её индексы перестраиваются, а база сохраняется целиком. Это осознанное ограничение учебной реализации.

**Как измерялась скорость?** На 1, 10 и 100 тысячах строк выполнялся одинаковый SELECT с forceScan и с индексом. После прогрева измерялись семь серий по сто запросов через System.nanoTime; бралась медиана средних времён. Создание базы, чтение файла, парсинг и печать исключались. Совпадение результатов двух способов проверялось до измерения.

**Почему по теннису мало таблиц?** Эта работа проверяет механизм СУБД. Участники, корты и бронирования дают нужные связи и все типы; тренеры и абонементы для требований не нужны.
